## B. Critical

### 1. An oversize clipboard is silently destroyed, and the restore reports success

`/Users/kabara/Desktop/Improve/Improve/Replacement/PasteboardTransaction.swift:186-193`

`snapshot()` skips any item whose payloads all exceed the remaining byte budget (`:109-112` `continue`, then `:116` `if !payloads.isEmpty`). When the clipboard holds one large item — a copied screenshot, a TIFF from Preview or Pixelmator, a video frame — `saved` ends up **empty** while `snapshotIsComplete` is false.

`restoreIfUnchanged()` then calls `pasteboard.clearContents()` unconditionally at `:186`, and the guard at `:189` reads:

```swift
guard !saved.isEmpty else {
    // The clipboard was empty before we started. Leaving it cleared is
    // the faithful restore.
    return true
}
```

`saved.isEmpty` conflates *"the clipboard was empty"* with *"we could not afford to save it"*. In the second case the function wipes content it never saved and returns `true`.

Reproduced against a private `NSPasteboard`, compiled from the file as written:

```
before: items=1 tiffBytes=41943040
snapshotIsComplete=false
restoreIfUnchanged returned true
after:  items=0 tiffBytes=-1 string=nil
```

This is the exact harm class root `AGENTS.md` §5 singles out — *"Anything the user copies during a rewrite is silently destroyed"* — arriving through a different door than the one that was guarded. It is worse than doing nothing: had the transient text been left in place, the user would at least see something changed. Instead the clipboard is empty, no signal is raised, and `snapshotIsComplete` is never read by any caller.

Both reachable call sites are affected: `pasteReplace` (`ReplacementService.swift:112`) and `copySelection` (`ClipboardSelectionAdapter.swift:131`).

The fix is to distinguish the two states — track whether any item was seen at all, and when the budget dropped everything, decline to clear rather than clearing and claiming a faithful restore. The in-file rationale at `:73-75` ("a partial restore still beats leaving our scratch content in place") is the reasoning that produced this; it is correct for a *partial* snapshot and wrong for an empty one.

## C. Important

### 2. The cached-clipboard shortcut bypasses the secure-role check

`/Users/kabara/Desktop/Improve/Improve/Selection/SelectionCoordinator.swift:122-129`, and `captureViaClipboard` at `:267-301`

The brief's first specific check was the pid-ownership fix, and that one holds (see D.1). This is the neighbouring hole.

On the uncached path the ordering is correct: `captureViaAccessibility` resolves the element, throws `.secureField` at `:168-171` before reading any text, and only a genuinely unreadable app (nil focused element) reaches the clipboard — where there is nothing to check, so nothing is lost.

The cached path is different. Once an app has been recorded as `.clipboard`, the next capture within ten minutes jumps directly to `clipboard.copySelection()`, which posts a synthetic ⌘C at `ClipboardSelectionAdapter.swift:117`. No focused element is resolved, no role or subrole is read. `captureViaClipboard` resolves an element at `:283` only *after* the text is already in hand, and never runs `isSecureElement` on it at all.

This matters because the cache is keyed per app, not per field. An app is recorded as `.clipboard` because its accessibility tree was unavailable at that moment — an Electron app before anything enabled its tree, say. If the tree becomes readable in the interim (another assistive app enabled it, or the user focused a different view) and focus is now in a password field, Everest posts ⌘C into it with only the global `IsSecureEventInputEnabled()` flag standing in the way. The implementer's own measurement establishes that an AppKit `NSSecureTextField` sets that flag; a web or Electron `<input type=password>` does not.

⚠️ **Cannot verify from the code alone** how exploitable this is in practice: it turns on whether the target toolkit refuses a copy from its password widget. Chromium and WebKit do block copy from password inputs; the Java, Qt and custom-text-layer toolkits this fallback was written for are exactly the ones with no such guarantee. Relying on the target app to protect the password is the kind of reasoning the rest of this directory correctly refuses to do.

Cheap fix, consistent with the existing design: resolve the focused element at the top of `captureViaClipboard` and throw `.secureField` if `isSecureElement` says so, before posting the keystroke. It costs one AX round trip on a path that already budgets 400 ms.

### 3. The `AXStringForRange` branch is unprotected against the off-by-one, and revalidation cannot catch it

`/Users/kabara/Desktop/Improve/Improve/Selection/SelectionCoordinator.swift:205-210`

The brief asked whether this unexecuted branch fails closed or open. **Mechanically it fails closed** — `stringForRange` returns nil on any AX error, `text` stays nil, and the chain moves to the manual-accessibility retry and then the clipboard. No write occurs in capture. That part is correct by inspection.

**Semantically it can fail open**, and the codebase's own documentation says why without noticing that it applies here. `Selection/AGENTS.md` describes the long-standing Chromium/Electron off-by-one in `AXSelectedTextRange`, and explains that `AXSelectedText` is preferred precisely because it does not go through that arithmetic. But this branch is entered *only* when `AXSelectedText` is empty — that is, in exactly the population where the preference offers no protection. A shifted range yields well-formed-but-wrong text, which no downstream validator can detect.

The revalidation cannot catch it either, and this is the part worth stating explicitly. `TargetValidator.compare` mirrors the capture chain on purpose (`TargetValidator.swift:117-121`): for such a snapshot it re-reads through the *same* shifted range and gets the *same* shifted string, returns `.matches`, and `apply` proceeds. Route one then writes `kAXSelectedText` over the **live selection**, not over the range that was read. The user's actual selection is replaced by a rewrite of text that was off by one character at one end. Identical exposure on route two.

There is no clean fix inside the AX API, so I am not asking for one. What is missing is the acknowledgement. `Selection/AGENTS.md` currently asserts:

> The range is still recorded, but only as an identity token for revalidation, never as a way to reconstruct the text.

That sentence is false for rung 7, which reconstructs the text from the range by definition. A future agent reading it will believe a protection exists that does not. The doc should state that the `AXStringForRange` route is the one place the off-by-one is unmitigated, what it costs, and that the four-identity check is structurally unable to detect it.

### 4. Both `AGENTS.md` files misstate or omit guards a future agent will trip over

Judged against root §0.4 ("rationale, not inventory") and §0.5 ("do not delete a guard because it looks like overkill"), these files clear the bar comfortably on style and mostly on substance. Three specific defects, in descending order:

**(a) `Selection/AGENTS.md` affirmatively misdescribes the refusal order.** The chain is presented as unconditional — *"**4. Secure role check.** The moment we have a focused element and before any text leaves it"* — and the strategy-cache section says only that a cached answer "is never a gate", framing the cache as a performance hint. Neither passage mentions that a cached `.clipboard` entry skips rungs 3 through 8 outright, including rung 4. The document's most emphatic claim — *"if you reorder the refusals you will read a password"* — is undermined by a reordering the document does not disclose. This is worse than an omission; it is a decision record that will be trusted and is wrong.

**(b) `Replacement/AGENTS.md` never records that blocking the main thread is load-bearing.** `Selection/AGENTS.md` does this well: *"The waits block the main thread and must not pump the run loop... pumping would let a second hotkey press re-enter the capture chain while the first is halfway through borrowing the clipboard."* `ReplacementService` has the same property and the same hazard — `observeConsumption` blocks up to 450 ms (`ReplacementService.swift:129-146`) and `pasteReplace` holds an open `PasteboardTransaction` across it — but `Replacement/AGENTS.md` says nothing about it. An agent told to fix a UI hitch would make `observeConsumption` async, which reads as an obvious improvement and silently opens a re-entrancy hole into the global pasteboard. This is precisely the "simplify away a guard" failure §0.5 exists to prevent, and the file has no defence against it.

**(c) The byte-budget edge case behind the Critical finding is undocumented.** `Replacement/AGENTS.md` explains the 16 MB budget and what `snapshotIsComplete` means, but never states what a restore does when the budget drops *everything*. The reasoning it does record — *"a partial restore still beats leaving our scratch content in place"* — is the reasoning that produced the bug.

Smaller: `snapshotIsComplete` is documented as *"Callers may log this"* and no caller does, so the flag is currently dead (`PasteboardTransaction.swift:76`).

What the files get right, and should be preserved in any revision: the "What is verified, and how" sections in both, which name the apps, the counts and the specific claims, and are explicit about which branches never ran. That honesty is rarer than the prose quality and is worth more.

## D. The brief's specific checks

### 1. The pid-ownership fix — holds, and cannot be bypassed ✅

`AXSelectionAdapter.swift:112-124`. The system-wide lookup at `:113-114` is a compound condition: the element is returned **only** if `self.pid(of: element) == pid`. If either the copy fails or the pid differs, control falls to the application-element lookup at `:119-121`, and `AXUIElementCreateApplication(pid)` can only vend an element belonging to that pid. Both exits are therefore pid-correct, and there is no third return path.

`focusedElement(pid:)` has three call sites — `SelectionCoordinator.swift:161`, `:283`, and `TargetValidator.swift:59` — and every one passes a pid that came from `NSWorkspace.frontmostApplication`, the same value the exclusion check was evaluated against (`SelectionCoordinator.swift:104-111`) or the snapshot's own pid after the frontmost check (`TargetValidator.swift:56`). There is no way to reach an element belonging to an unchecked process.

Note this is defence-in-depth, not the primary exclusion guard: the exclusion refusal already happens before any AX call. Its value is against a focus that has wandered to a helper process mid-chain. Correct as written.

### 2. Conditional pasteboard restore — genuinely gated, no surviving fixed delay ✅

`PasteboardTransaction.swift:173-211` is the only restore in either directory. It requires `didSnapshot` **and** a non-nil `expectedChangeCount` (`:174`), then requires `pasteboard.changeCount == expected` (`:176`); on mismatch it discards and returns false without touching the pasteboard (`:181-183`).

Both ways of setting the expectation are correct for their case. `writeTransient` reads `changeCount` after both `clearContents()` and `writeObjects()` (`:149-153`), which is the robust ordering. `expect(changeCount:)` adopts the target app's count after a synthetic copy (`ClipboardSelectionAdapter.swift:130`), which is the only thing it can do when somebody else was the writer.

Grep for `asyncAfter`, `Timer`, `RunLoop`, `CFRunLoop`, `DispatchQueue`: no hits in either directory. The only `Thread.sleep` calls are poll granularity (8 ms) and the 100 ms AX-tree settle — neither is a restore delay. The `defer { discard() }` at `:187` is placed after `clearContents()` and before the `saved.isEmpty` guard, so it fires on both exits correctly.

The guard holds. Its failure mode is the *snapshot* side, not the restore side — Critical finding 1.

### 3. Re-entrancy — cannot interleave, for a reason that is real but fragile ✅ (with a caveat)

`capture()` is `throws`, not `async`, and contains no suspension point. Every wait is `Thread.sleep`, which does not pump the run loop. Carbon hotkey events and `NSEvent` dispatch arrive through the main run loop, which is blocked for the duration. A second ⌘I therefore cannot begin until the first returns. The same holds for `apply`.

State ownership is also clean independent of that: both `PasteboardTransaction` instances are function-local (`ClipboardSelectionAdapter.swift:113`, `ReplacementService.swift:99`), never stored, never shared. No snapshot state can be corrupted by another instance.

What *would* be corrupted under re-entrancy is the global pasteboard — an inner transaction would snapshot the outer transaction's transient text and later "restore" that as the user's clipboard. So the blocking design is the only thing standing between the app and that outcome. It works, and `Selection/AGENTS.md` records why; `Replacement/AGENTS.md` does not (Important 4b).

⚠️ **Cannot verify from the code alone:** whether `AXUIElementCopyAttributeValue` pumps the main run loop internally while awaiting its reply. The HIServices implementation is closed. If it does, it uses a private mode, and hotkey and `NSEvent` sources live in the common modes, so delivery during an AX call remains very unlikely — but this is an assumption, not something the source proves.

### 4. The two unexecuted branches

**`AXManualAccessibility` retry — correct by inspection, fails closed.** `SelectionCoordinator.swift:245-263`. The `allowed` flag terminates recursion after exactly one retry (`:251`, set false at `:256`). A refused attribute write returns nil and falls through to the clipboard (`:252`). A throw from the inner call — `.secureField`, `.noSelection`, `.tooLong` — propagates and aborts the capture, which is right: after the tree is up, an app reporting a zero-length selection is telling the truth. On success it correctly overwrites the inner `record` with `.manualAccessibility` (`:261`). No write to any target occurs on any path.

Two observations, neither a defect: the flag is left enabled on the target process even when the retry yields nothing, permanently changing a third-party app's accessibility mode as a side effect of a failed capture (the persistence is documented; leaving it on after failure is not). And the `cached == .manualAccessibility` branch at `:131-133` sets the attribute without the 100 ms settle, so a relaunched process costs one redundant set before the retry path does it properly — self-correcting, no correctness impact.

**`AXStringForRange` — fails closed mechanically, can fail open semantically.** Covered in Important 3.

## F. Explicitly not treated as defects

Per the brief, and I agree with each:

- Directories still named `Improve/`. The central rename is pending and is not this task's job. Both `AGENTS.md` files use "Everest" as the product name and `Improve/` for paths, which is the correct state mid-rename.
- `pasteReplace` verified by composing its parts rather than executing the whole function. The composition order in the source matches the order the implementer reports testing, and I read it line by line without finding an assembly error.
- A clipboard-captured selection always ending in `.copiedOnly`. The code justifies it (`TargetValidator.swift:97-123`: no range and no readable selected text means no route to `.matches`, and `unknown` is a refusal) and both `AGENTS.md` files state it plainly as intended. The reasoning — cannot read the app, therefore cannot prove where a paste would land — is sound, and the `.copiedOnly` promise is kept in every such case.

## Summary of required changes

1. **Critical** — fix the empty-versus-dropped conflation in `restoreIfUnchanged` so an unsavable clipboard is not wiped and reported as restored.
2. **Important** — check `isSecureElement` before posting the synthetic ⌘C on the cached-clipboard path.
3. **Important** — document that the `AXStringForRange` route is unprotected against the Chromium off-by-one and that revalidation is structurally unable to detect it; correct the "never a way to reconstruct the text" sentence in `Selection/AGENTS.md`.
4. **Important** — `Selection/AGENTS.md`: disclose that a cached `.clipboard` entry skips rungs 3-8. `Replacement/AGENTS.md`: record that blocking the main thread is a re-entrancy guard, not just a cost, and that the 16 MB budget has an all-dropped edge case.

Items 3 and 4 are documentation changes, and under root §0.2 they belong in the same commit as the code fixes for 1 and 2.
