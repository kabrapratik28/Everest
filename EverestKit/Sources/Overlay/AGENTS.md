# Overlay: the floating panel

Borderless panel at the bottom of the screen; streams the rewrite in, goes away. `show(_:)`, `update(_:)`, `update(from: RewriteEvent)`, `dismiss()`, `onCancel` / `onPickStyle` / `onCopy`.

Almost none of a floating panel is about windows. Words, icons, placement, the height cap, auto-dismiss, throttling, key mapping: arithmetic and lookup, all tested. `Seams.swift` holds the entire boundary — `PanelSurface`, `KeyMonitoring`, `PanelClock`. Below it sit `NSPanelSurface`, `RunLoopPanelClock`, both `KeyMonitoring` adapters (`NSEventKeyMonitor` observes, `CGEventTapKeyInterceptor` consumes), `PanelAppearance.current()` and the two SwiftUI views: no decisions, no tests, hand-checked. **Nothing below a seam decides anything.** An `if` in `RewriteView` about *what* to show, or a number in `NSPanelSurface` about *where*, belongs above it — that rule is what keeps the untested part small.

## Never key, in any state

`.nonactivatingPanel` + `.borderless`, and `canBecomeKey` is false everywhere. Activating makes the source app resign active. Its selection stops being live, `AXSelectedText` goes empty or stale, and capture fails — no crash, no log line, no failing test. Make it a plain `NSWindow` and the product silently stops working. Hence also `hidesOnDeactivate = false`, `becomesKeyOnlyIfNeeded = true`, and `orderFrontRegardless()` over `orderFront(_:)` (an inactive app's can be deferred). `.borderless` is part of the guard: a titled window can become key. **Terminal states did take key status for a while**, via `makeKey()` in `present`, because only a key window can consume and ⌘C had to be kept from the source app — `canBecomeKey` is permission, not action, and nothing had been asking. It worked, and it was the wrong trade: **a key window receives *every* keystroke**, this panel answers none of them, so ⌘V died in an empty responder chain and the state whose own headline is "Press ⌘V to paste your rewrite" was the one preventing the paste. Measured against TextEdit — with `makeKey()` a ⌘V put nothing in the document; without it the clipboard pasted, with the tap armed and consuming ⌘C. So consumption belongs to the tap, which takes only the keys it acts on, and the panel is never key again. What the tap is armed for, from `PanelState.needsKeyInterception`:

| State | Tap | Why |
|---|---|---|
| `stylePicker` | yes | its digits and arrows would otherwise land in the document about to be rewritten |
| `readOnly`, `targetChanged`, `heldForManualCopy` | yes | ⌘C must not also reach the source app, whose own Copy lands *after* ours and overwrites the rewrite |
| everything else | no | nothing to take — `refused` and `error` hold no rewrite, and a tap armed for nothing is pure hazard |

## Keys come from an `NSEvent` monitor

A non-key panel has no first responder, so `.onKeyPress`, `.keyboardShortcut`, `@FocusState`, `List(selection:)` and `cancelOperation(_:)` all do nothing — each looks right in an Xcode preview, where the host *is* key. That is why `StylePickerView` is a `VStack` over a plain `Int`. Two monitors: **global** (another app frontmost — the normal case) and **local** (global monitors never see our own process, so without it Escape dies exactly when the user is looking at us). Only the local one can consume, by returning `nil`.

**Teardown is structural, not disciplinary.** A global key-down monitor watches every keystroke in every app while installed; "remember to remove it" is a habit, not a guarantee. `install` returns a `KeyMonitorHandle` whose `deinit` removes them, and the controller holds the only reference — clearing it removes them, releasing the controller removes them. No reachable state has them installed with the handle lost. Four tests hold that, including the error path and controller deallocation. Monitors stay armed through terminal states until `dismiss()`, so a result panel on its timer still closes on Escape.

**Observe vs. consume — the most important fact in this directory.** A global monitor observes: `addGlobalMonitorForEvents` takes no verdict back, so every arrow, digit and Return in the picker *also* reached the frontmost app. The arrows moved its caret and collapsed the selection about to be rewritten; a bare digit **replaced the selected text with that digit**. Measured, not argued: TextEdit holding a selected `ORIGINAL` came out reading `34`. The obvious fix is wrong — making the panel key consumes the keys but costs the source app frontmost, which is exactly what `TargetValidator` checks, so every rewrite downgrades to `copiedOnly`. That is one of two reasons no state is key, the picker least of all. A `CGEventTap` at `.cgSessionEventTap` with `.defaultTap` consumes by deleting the event from the session ahead of dispatch to any app, so it costs nothing in focus: the same measurement with one installed leaves TextEdit reading `4`, with TextEdit frontmost throughout. `CGEventTapKeyInterceptor` is that tap. Rules it must keep: armed from `state.didSet` for the states in the table above **and no others**, released by the same `KeyMonitorHandle` ownership as the monitors, because a leaked tap deletes keystrokes in every app forever — its lifetime is a state, not a transaction; it claims only what `PanelKeyMap` resolves, so every other key passes through untouched; a key it consumed never reaches our own global monitor either, so nothing is acted on twice; and it **re-enables on `.tapDisabledByTimeout`**, because the system switches a slow tap off without a word — measured at 1 of 8 keys seen after a stall, 7 of 8 with the re-enable. `handle` (monitors) ands what it did with `acceptsKeyWindow`, now false in every state, so the monitors act and never claim; `intercept` (tap) returns `acted`. **`acceptsKeyWindow` is therefore a constant**, and it plus `present`'s `acceptsKey` parameter are deletable — that changes `PanelSurface`, so it needs the lead's sweep rather than a quiet edit. **What ends the tap.** `stylePicker.autoDismissAfter` is `nil`, so nothing closes the picker by itself and the tap would outlive the user's attention — still swallowing digits, arrows and Return in whatever app they moved on to, and picking a style from a keystroke meant for Slack. So a key the picker *cannot answer* ends it, and that key passes through untouched. Deliberately not a timer: `autoDismissAfter` is read by the coordinator and by `keyHints`, so giving the picker one would silently delete its visible `esc` hint, and a timer would not catch the real case anyway — a user typing somewhere else minutes later. **The tap is not dropped on the spot**; that was tried and reopened the original bug. Only the coordinator can dismiss, and it gets there through an `await`, so for at least one actor hop `state` is still `.stylePicker` and every picker key still resolves — with the tap already gone, a digit in that gap reached the document and replaced the selection again. `pickerIsSpent` makes the gap *inert* instead of racing it: **the picker answers once**, whether Return, Escape or an unanswerable key ended it, and anything arriving after is swallowed and does nothing. Reaching the key map is not success either — Return and the arrows resolve against a picker with **no rows at all**, and counting those no-ops as answers let an empty style list (nothing stops a user deleting every style) swallow them for as long as the panel stayed up. So a key the picker owns but cannot apply is consumed and ends it, because it was aimed here and a leaked Return submits a form; a key it never claims is passed on. **Standing down belongs to the picker alone.** A panel holding a rewrite is not a question — it is the user's only copy, `autoDismissAfter` is `nil` for that reason, and carrying the rule across would let any stray keystroke anywhere cancel the transaction and throw the rewrite away. **And the whole thing fails closed.** `tapCreate` returns nil without Accessibility, and an inert handle indistinguishable from a working one left the monitors *executing* while unable to consume — the original bug, with the picker appearing to work and the document being edited underneath it. `KeyMonitorHandle.isActive` asks the tap rather than recording that creation succeeded, so a tap the system switched off answers the same as one that never existed and `.tapDisabledByUserInput` needs no second mechanism. Where a state needs interception and there is none, the monitors act on **Escape and nothing else**: a leaked Escape is harmless, and without it the keyboard has no way out of a panel that has stopped answering. Doing nothing visibly beats half-working in the user's text.

> **For the app shell: still capture the selection *before* showing the picker.** The tap is the guard, not a reason to drop the cheaper one. It used to be that a revoked grant leaked the keys again; now the panel **fails closed** instead — but the ordering still costs nothing and is the only thing standing between a stray digit and the document if this ever regresses.

**⌘C, never Return.** Return is too dangerous for a convenience binding: if the key-window logic ever regressed, a leaked Return sends a Slack message or submits a form. A leaked ⌘C copies the frontmost app's own selection, which is harmless, and it is the universal idiom. Consuming still matters — if the panel were not key, the frontmost app's own copy would land *after* ours and overwrite the rewrite on the clipboard. **Consumption is decided from the state the keystroke was dispatched against**, captured before the action runs. The panel can go down mid-keystroke — a verified `copy()` dismisses synchronously, so `state` is `nil` before the keystroke has finished being answered — and reading `state` afterwards answers "not consumed" for a ⌘C just performed, which lets the frontmost app's own Copy land over the rewrite in the one state holding the user's only copy. The stub that merely records the text is quieter than the app and passed throughout, so one ⌘C test now dismisses the way production does. `Keystroke.isPlain` is false when any of ⌘⌥⌃⇧ is held, so ⌘3 and ⇧3 pass through; ⌘C requires *exactly* ⌘. Picker keys do nothing outside the picker. Rows are numbered to nine, since `AppSettings.styles` is user-editable and uncapped and anything past the numbered rows is arrow-only.

**Shortcuts are shown, or they do not exist.** This panel is up for two seconds with no menu bar, tooltip or onboarding. `PanelState.keyHints` is tested per state: ⌘C wherever there is a rewrite to copy, `esc` wherever the panel will not close itself. Each hint carries `performs: PanelKeyAction`, because **the hint row *is* the clickable control** — one affordance showing the shortcut, carrying the words and taking the click, rather than a button beside a caption (which left a bare glyph in one corner and its label in the other). Matching on the displayed words instead would break the first reword. Badges are keycaps — shape and weight, never colour alone — and `.accessibilityHidden(true)`, since a screen reader announces key equivalents through the standard mechanism.

## Bottom centre, not the caret

Caret anchoring needs `kAXBoundsForRangeParameterizedAttribute`, which rests on the same range reporting `TextBridge` documents as unreliable: many apps do not implement it, Chromium and Electron are inconsistent, and it returns empty rects, wrong coordinate spaces or scrolled-out lines — putting the panel off the display. A panel you cannot see is worse than a boring one. `PanelGeometry` is a pure function of a `CGRect`, so screens nobody has plugged in are testable. Its tests use a **negative-origin** screen: a frame from `width / 2` instead of `midX` passes at the origin and fails on a second display. The screen comes from the pointer, not `NSScreen.main` (that is the key window's screen), and is sampled once at `show()` so a growing panel cannot hop displays mid-stream. `minY` is constant per screen, so the panel grows upward rather than crawling down it. Height follows content to 40% of the visible frame, then `PanelLayout.scrolls` goes true and the document keeps its full height so the overflow is reachable rather than clipped. Width, inset and cap are clamped to the visible frame, because 40% of a short screen plus a fixed 96pt inset stops fitting.

## Streaming is throttled to ~16 ms

A 4B model emits faster than 60 Hz and every event is a full cumulative snapshot, so rendering each one relayouts a growing paragraph dozens of times a second against the decoder on the same thread. Dropping an intermediate snapshot is free — the next is a superset.

| Rule | Without it |
|---|---|
| The held snapshot is flushed on a timer | The last tokens never render; the rewrite stops a few words short |
| Only `generating` is throttled | A terminal state waits behind a timer showing a stale spinner |
| A non-streaming state clears the held one | A queued snapshot lands after the result and overwrites it |

Timer on `RunLoop.main` in `.common`: a default-mode timer stops firing while a scroll gesture or menu is up, freezing the text. Streaming auto-scrolls to the tail but stops once the user scrolls up — yanking someone back mid-sentence is worse than not following. The scroll position arrives through a `boundsDidChangeNotification` observer held in a `KeyMonitorHandle`, same ownership rule as the key monitors, because an observer nobody owns is that hazard one layer over; `postsBoundsChangedNotifications` must be set or it never fires. "At the bottom" is a *tolerance*, not an equality: offsets are fractional, so `==` would switch following off on the first gesture and never resume. `update(from:)` maps `.finished` to `.applying`, never to a terminal state: generation stopping is not the transaction succeeding, since validation and replacement still follow and can still fail. **`show()` resets the coalescer and deliberately does not also cancel the clock.** Either alone stops a superseded transaction's held snapshot flushing over the new panel — `flush()` is the only reader of `held`, so a cancelled timer never reaches it and a fresh coalescer has nothing to give it — which by §1 made one redundant. The reset stayed because it has a second reason: the held snapshot is the user's rewrite, and keeping it past the transaction is the thing root §6 forbids. Cancelling as well also *hid* the test, since a timer that cannot fire proves nothing about the coalescer. `dismiss()` still cancels, because nothing resets the coalescer there.

## `heldForManualCopy` must never close itself

`autoDismissAfter` is `nil` for it and must stay `nil`. It is the state where the rewrite could be neither written back nor put on the pasteboard, so the panel holds the user's **only** copy and a timer deletes their work. `success` is the opposite: **visible, and the briefest of the states that dismiss.** The tick is wanted — it acknowledges the replacement rather than reporting what the document already shows — so `.zero` is wrong, because at zero it renders for one frame and nobody sees it. 1200 ms was also wrong, because it sat on the text the user had just asked to look at. It is pinned by two relations and not by its number, which has already moved twice: above zero, and below every other dismissing state. 500 ms over the other candidate of 1 s, because the tick is a state *change* on a panel that has been streaming for seconds — the eye catches the flip, not the duration, where something appearing cold would need longer — it lands in the same instant as the text changing, so there are two signals, and 1 s is within 200 ms of the 1200 that prompted the complaint. **1 s is the sanctioned fallback** if the manual check says 500 reads as too quick, and swapping it needs no test change. It is also *presented* rather than skipped, and that is a separate reason — a screen reader user gets nothing from the document changing, so this is the only announcement the replaced path makes. The test asserts the rule across all eleven states, so a twelfth that quietly holds text fails it. **And copy closes it on evidence, never on the attempt.** `onCopy` reports a *read-back* of the clipboard and `copy()` dismisses only on true, because a write that silently did nothing — or landed and was overwritten a moment later — otherwise takes the clipboard and the panel together, leaving the user neither. Deliberately not the `Bool` from `writeObjects`: five attempts could not make it return false, and its one documented failure throws instead, so a checked return would add a branch no test can enter in the file that can least afford one. Evidence that the text is *there* covers all three, the throw included, since a dismissal that never happens is safe. A dismissal that never happens is recoverable — the user presses ⌘C again; one that happens too early is not.

## Accessibility is a requirement, not polish

`PanelAppearance` is three booleans and every consequence is a pure function of them: Reduce Motion drops the transition and indeterminate spinners (a *determinate* bar stays — position, not motion for its own sake); Reduce Transparency goes opaque, because translucency over arbitrary content is the worst thing you can do to contrast; Increase Contrast thickens borders and strips decorative tint. Read from `NSWorkspace`, not the SwiftUI environment, which is not populated for an `NSHostingView` in a non-key borderless panel. Sampled once per `show()` — an observer is one more thing to leak. **No state is signalled by colour alone**: a green check and a red cross at 14pt are the same grey glyph to one man in twelve. Two mechanisms, both needed — `symbolName` and `title` are `switch`es with no `default` (the compiler demands them), and `PanelStateKind` is a `CaseIterable` mirror so one test demands every case be *sampled and checked*, which the compiler cannot force. `accessibilityValue` omits the streaming text, because VoiceOver restarts its utterance on every change and would read the first three words at token rate; it does include refusal and error reasons, since a reason nobody can hear is not a reason. **None of those labels reach anyone on their own.** A non-activating panel takes no focus, so VoiceOver never visits the panel and every message it showed was silent — which, in an app built on the Accessibility API, is the one irony worth spending a seam on. `PanelSurface.announce` posts `.announcementRequested` against `NSApp`, not the panel, which is usually not in the focus chain, and at `.high`, because a medium announcement is dropped whenever VoiceOver is already speaking and this panel is gone in seconds. `FloatingPanelController` calls it once per `PanelStateKind` and not per render: per render would restart the utterance at token rate, and an arrow key redrawing the picker would talk over the row the user is trying to hear.

## Things that will look like cleanups

Dropping `.nonactivatingPanel`, or making the panel key in *any* state — `makeKey()` in `present` is what swallowed ⌘V · carrying the picker's stand-down rule into a panel holding a rewrite · binding Return to anything · `.onKeyPress` instead of monitors · keeping monitors armed between transactions · dropping the local monitor · returning `true` from `handle` unconditionally · widening the tap past the states in the table, or past the keys `PanelKeyMap` claims · dropping the `.tapDisabledByTimeout` re-enable · letting the picker outlive a key it cannot answer · dropping the tap the moment the picker is answered instead of leaving it to `dismiss()` · treating "the key map resolved it" as "the picker answered it" · reading `state` after running a handler to decide anything about the keystroke that ran it · letting the monitors act on a key the tap is not there to take · announcing per render rather than per state kind · hiding the keycap badges as "clutter" · putting `clock.cancel()` back into `show()` as belt-and-braces · collapsing the seams ("the indirection buys nothing" — it is why 77 tests exist here) · rendering every snapshot · deleting the flush timer ("the next token will render anyway": there is no next token after the last) · auto-dismissing `heldForManualCopy` · dismissing on the copy attempt rather than on a read-back · lengthening `success` back towards the others, zeroing it so the tick never renders, or skipping its presentation (the announcement goes with it) · caret anchoring · treating Reduce Motion as optional.

**Tests:** `cd EverestKit && swift test --filter OverlayTests`. While other agents are mid-RED, isolate with `swift build --target OverlayTests && xcrun xctest .build/out/Products/Debug/OverlayTests.xctest` — and check the build succeeded, because `xctest` will happily re-run the previous bundle. `PanelKeyWindowTests` is the one suite that opens a real window and needs a window server; it is also the only place the adapter's key-window behaviour can be checked at all, which is why it earns the exception.
