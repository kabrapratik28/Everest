# TextBridge

Reads the selection out of another app and writes the rewrite back. Highest-risk code in Everest: a bug here leaks a password into a prompt or destroys a document with no undo on either side. Biased toward doing nothing when uncertain.

## Capture chain, in order (`SelectionCoordinator.capture`)

| # | Rung | Why it sits here |
|---|---|---|
| 0 | `IsSecureEventInputEnabled()` | Free, no permission, true exactly when we must stay out. Synthetic keys stop being delivered anyway. |
| 1–2 | Frontmost app, then `excludedBundleIDs` | Refused before any AX call is aimed at the app. Case-insensitive and exact; prefix matching would let `com.apple` exclude everything. `var`, because Settings edits it while running. |
| 3–3a | `AXIsProcessTrusted`, resolve focus | Rung 4 needs an element, and the apps hiding passwords are the ones whose tree is off. |
| 4 | Secure **subrole** refusal | See facts. Before any text read and any keystroke. |
| — | Strategy cache lookup | **Only here.** Skips work, never a refusal. |
| 5 | `AXSelectedText` | The app's own answer. Beats anything reconstructed from a range. |
| 6 | `AXSelectedTextRange` | Read before rung 5 in code: a range is not the user's characters, and it is the only thing that disambiguates rung 5. Zero length ends *this element*, not the chain. |
| 7 | `AXStringForRange` | Sets `isRangeDerived`. Never written back. |
| 8 | `AXManualAccessibility`, retry **once** | Chromium and Electron. Re-runs the secure check on the revealed tree. |
| 9 | Synthetic ⌘C | Last: only path that disturbs the clipboard, and the target's write leaks to clipboard-history apps. |

One length check at the end, not per rung, so a new rung cannot forget it: over 8,000 characters throws `.tooLong(count)`. Proved on all three routes, because a test that only ever arrives by rung 5 pins a choke-point check to rung 5 — and rungs 7 and 9 are the whole copy-only column of root §3.

## Facts that were expensive to learn

| Fact | Consequence |
|---|---|
| A real `NSSecureTextField` is role `AXTextField`, subrole **`AXSecureTextField`** | A role-only check reads the password. Check both slots. |
| Chrome 153 **does** set `IsSecureEventInputEnabled()` for `<input type=password>`, and a synthetic ⌘C extracts nothing from one | Both measured, with a control on an ordinary field in the same browser (flag false, ⌘C works). The copy refusal is the one that matters, because it holds even with no AX element — which is the only state where rung 9 is reachable. **Do not generalise the flag**: Chrome-the-app sets it at `NSApplication` level and nothing obliges another Chromium host to, so the subrole check stays the guard you rely on. This row previously asserted the opposite, that web and Electron password fields never set it — false, and an external auditor quoted it back as the premise for a P0 that did not exist. A version-bearing measurement, so treat it as rottable. **Unmeasured:** Electron, and any app with no tree, no flag *and* a copyable password field; native `NSSecureTextField` and Blink both refuse. |
| `AXFocusedUIElement` on the system-wide element can return `kAXErrorCannotComplete` on macOS 26 while the per-app query succeeds | Ask both. Require the answer's pid to match the frontmost app on **both** branches: that check is a *security* check, since the exclusion list was evaluated against that process. The fallback was once returned unchecked, which put the hole in the branch that exists *because* the system-wide query is unreliable — i.e. the one ordinary apps take. `focused(systemWide:perApp:ownedBy:)` is split out so the branch can be driven; `perApp` is an autoclosure to keep the short-circuit, since it is a synchronous cross-process call. |
| Chromium's `AXSelectedTextRange` is off by one | Rung 7 text is shifted but still well-formed prose, so nothing downstream detects it, and revalidation re-reads the same shifted range and agrees with itself. Hence `isRangeDerived` forces copy-only, refused **before** the validator so nobody reads a pass as permission. |
| Chromium builds no AX tree until asked | Rung 8 writes the undocumented `AXManualAccessibility`. The tree is not ready when the call returns: settle, re-resolve, retry once. A loop is a visible freeze. Not `AXEnhancedUserInterface`, which also changes window management. |
| `AXSelectedText == ""` is ambiguous: nothing selected, or the wrong element | The range settles it, but only about *that element*. Length 0 **and the element holds characters** → stop with `.noSelection`; length 0 **and it holds none** → hand to the next rung; >0 → rung 7; absent → rungs 8–9. Falling through on a genuine empty selection rewrites whatever the user copied ten minutes ago; *not* falling through loses **Google Docs**, which has painted its text into a `<canvas>` since 2021 and parks focus in an empty `contenteditable` in an offscreen iframe. Measured, Chrome 153: `{0,0}`, `AXSelectedText ""`, `AXNumberOfCharacters 0` — all true of that element, none about the sentence the user highlighted — while ⌘C returns it normally. A *missing* count is not zero; handing off needs positive evidence. Docs is therefore rung 9, so `.copiedOnly`, and no AX route will ever replace in place there. **That is a measurement, not a contract.** Nothing obliges Chrome to keep reporting 0 there; if it stops, Docs silently returns to the old `.noSelection` refusal — a regression indistinguishable from the original bug, and one **no test here can catch, because the fake is where the number comes from**. A test whose input is the thing that might change is not a regression test for that change. Manual check 19 (IME composition) is the near-term probe of the same exposure. |
| Under App Sandbox `AXUIElementSetAttributeValue` does nothing, the prompt never appears, and `AXIsProcessTrusted()` is permanently false | **No degraded sandboxed mode exists.** Do not add the entitlement. If asked to make this sandbox-compatible, say plainly that it means deleting the feature. |

## Guards that must not be simplified away

| Guard | What breaks without it |
|---|---|
| Cache lookup **below** the secure refusal, and `.clipboard` recorded **only** for an app whose tree stayed dark | A warm `.clipboard` entry posts ⌘C at a password field. The cache is per app, not per field, so focus can move into one with the entry still warm: a cached answer is a hint, never a gate, and expiry plus version-invalidation keep a bad reading from being permanent. It is also not one text engine — Chrome is Google Docs *and* Gmail, so learning ⌘C from Docs would cost Gmail its in-place rewrite for ten minutes, a downgrade to copy-only nobody can see or undo. An app that resolved focus on the first ask is not the hostile app the cache exists for — **and it is consulted only while the app is still dark, for the same reason**. Otherwise the entry is self-sustaining: a cached hit returns before accessibility is asked, so the route that would replace it never runs, and an app whose tree came back stays copy-only for the rest of the interval. The fall-through only rescues an app whose *clipboard* route stopped working, never one where both work. **And the rung-8 re-check on the revealed tree is the only guard left on the Chromium path**: rung 0 cannot be relied on, because that flag is per-host — Chrome 153 sets it, nothing obliges an Electron app to — and rung 4 was skipped for want of an element — which is exactly why rung 8 ran. Deleting that line left all 74 tests green until `revealedTreeIsRecheckedForASecureField` existed, because the one fixture that reached it revealed an ordinary text field. |
| Restore gated on `changeCount`, never a delay — and the give-back happens at **every** exit | A delay races the user's ⌘C and silently eats it: no delay is short enough to win or long enough to be safe, because the hazard is a user action, not a duration. `expect(changeCount:)` covers the case where the *target app* was the writer. **A budget bounds how long we wait, never how long we stay responsible** — the principle both posted keystrokes are governed by, and the recurring defect here, three times now. **(a)** `copySelection` used to return the moment the copy budget expired **without restoring at all**; the fix is that the give-back now happens on every exit, and the watch runs to `copyBudget + settleBudget`. Measured, Chrome's first ⌘C after launch took 262 ms of 400 ms, so "late" is an ordinary cold start, not a pathological app. **Past 520 ms this is a limit, not a fix, and the residual is real:** we have stopped watching, and a target answering then overwrites the clipboard we put back. Unlike the paste path we cannot simply hold — a target that never answers ⌘C would block forever — so the deadline is the most responsibility this path can take, and a longer one buys a rare case with a certain main-thread freeze on every app that cannot answer. What lands there is the user's *own selection*, not something foreign, which is why it is tolerated where the paste-side equivalent was not. **Do not read the principle above as a closed class.** The same window has a second open edge: any process moving the change count inside it is taken for the target answering our ⌘C, so a clipboard manager, a sync tool or Universal Clipboard writing just then is captured *as the selection* and rewritten. `NSPasteboard` does not say who wrote, so there is nothing to check — the borrow makes our own transactions exclusive and can do nothing about anyone else's. Widening the budget widens this too; that was the price of the give-back above. **(b)** Restore only if something actually wrote; `abandon()` otherwise, because rewriting identical bytes bumps `changeCount` and leaves a duplicate clipboard-history entry per hotkey press in an app that cannot answer. **(c)** Declining to restore is still a logical end, so it releases too, **and the caller must then not hand off** — a declined restore means the user copied something while the rewrite ran, and `handOff` would write the rewrite straight over it. That is `.heldForManualCopy(.clipboardChanged)`: nothing touched, panel keeps the only copy. Note the ordering of these two: releasing the borrow is what *let* `handOff` succeed, so the fix for the leak converted a false error message into data loss. A fix that removes a wrong answer can hand the next stage a right of way it never had. Without the release — without that, `pasteReplace`'s `handOff` on the next line could not borrow and told the user another rewrite held the clipboard, which was false, and withheld the rewrite instead of copying it. **The general form, which is why `hold` blocks rather than deferring:** when work outlives the call that started it, ask not only whether the work is still correct but *what the resource it holds tells the next caller*. A borrow kept past the return turns "please wait" into "another rewrite is using the clipboard" — a false error about a resource nobody holds, and the kind that gets debugged for an hour. It hides because **tests do not press the button twice in 450 ms**. |
| `canBorrow` checked **before** anything writes | By `restoreIfUnchanged` the bytes are already gone from both your copy and the pasteboard. Both call sites check first; the refusal inside restore is only a backstop. |
| Snapshot every type on every item, ordered | Type order is preference order, so string-only silently downgrades a copied table to tab-separated words. **Three writes, three different marking rules.** The scratch write is always transient and auto-generated. The restore is *never* marked, because that content is the user's own and marking it would make a manager drop their real clipboard from history. The durable `copiedOnly` write is marked only when the user has asked to keep rewrites out of history — the markers stop *recording*, not pasting, so the `copiedOnly` promise survives either way. Never `ConcealedType`: the convention reserves it for passwords and some managers warn on it. |
| A rung-9 target is pasted into only after a **re-read**, and never if it inserts rather than replaces | `.copiedOnly` promises a *durable* write, so copy-only destroyed the user's clipboard on every rewrite in an app like Sublime — measured, it exposes no editable element at all, so every rewrite there took that path. The fallback cost more than the risk it avoided. Auto-replace therefore pastes: ⌘C again first, and only if the same text comes back has the selection demonstrably not moved. That is *stronger* than the refusal it replaces, not a waiver — and `validate` still runs, so `.notFrontmost` and `.secure` are never overridden, only `.unverifiable`. Confirmed by a third ⌘C, because `observeConsumption` cannot work without an element: a landed paste leaves nothing to copy. Failure at any step is `.heldForManualCopy(.notPasted)` — panel keeps it, clipboard untouched — never `copiedOnly`, whose durable write is the thing being avoided. **Terminals are the one bundle-id list in this module** and the entry test is "paste *succeeds* and does not replace": ⌘V inserts at the prompt, so every signal says it worked while a rewrite ending in a newline has run as a command. A PDF needs no entry — it ignores the paste and the confirmation catches it. Not a denylist to grow; an exotic terminal goes in the user's exclusion list. **Rung 9 reaches the validator by two routes and they look nothing alike.** A terminal resolves no focused element, so it stops at `.unverifiable`; Sublime resolves one — an `AXWindow` — and `CFEqual` against `readViaClipboard`'s *application* element is then false, so it stopped a line earlier at `.focusMoved`. Same fact, different door, and the override keyed on only one of them, so it never fired for the app it was built for. `validate` now skips `CFEqual` for a `viaClipboard` snapshot, where the answer is manufactured rather than observed. **Fixed there and not in the caller because `CFEqual` precedes the secure check**: accepting `.focusMoved` as a paste signal would have pasted into a password field nothing had looked at. |
| `isEditable` is a veto only when auto-replace is off | With it on, route two is attempted regardless — the weakest signal in `apply` stops overruling the strongest. By that line the validator has proved the focused element reports our exact text *at our exact range*, and WebKit `contenteditable` accepts typing while reporting nothing settable, so those targets were handing the user a clipboard for no reason. **Safe because of what cannot reach the line, not optimism:** a rung-9 snapshot has a nil range, `compare` answers `.unknown`, and the validator refuses it — every terminal, PDF and Google Doc is rung 9, so none can be pasted into. Rung 7 is refused earlier by `isRangeDerived`. If the target really is read-only the paste is ignored and the outcome is the same copy-only, one budget later. Note `isRangeDerived` is **not** what excludes rung 9; it is `false` there, and reading it as the guard is how someone removes the real one. |
| Revalidate pid, element, range and text before writing, with `CFEqual` not `===` | Three seconds is enough to click elsewhere. Two references to one element are equal but not identical, so `===` would refuse every rewrite. No age limit: the identities are what make it safe. `unknown` is not `matches`, so a clipboard-path capture can never be written back. |
| Route one never chains into route two | A false-negative confirmation pastes the rewrite **twice**. A duplicated paragraph is unrecoverable; a rewrite that quietly did not land is visible and repeatable. |
| `PasteboardBorrow` makes a borrow exclusive per pasteboard | Two transactions must never interleave. A nested one snapshots **our own scratch text** as if it were the user's clipboard and restores that, and every `changeCount` check passes, because under re-entrancy the other writer is us. Blocking the main thread in `observeConsumption` also prevents it, but that is scheduling rather than correctness and it dies the moment someone adds a suspension point to kill the 450 ms hitch. Refused, not queued: both run on the main thread, so waiting deadlocks. |

## Outcomes, seams, verification

`CaptureError.noSelection` is the app's answer — an element holding text reported none selected — and `.nothingCaptured` is ours, meaning every rung including ⌘C came back empty. Kept apart because which of the two it was is exactly what we could not determine, and offering only "select some text" to someone looking at their own highlighted paragraph sends them to reselect forever. `.clipboardUnavailable` is a third thing again: rung 9 never ran, because the clipboard held something we could not have put back. The app is fine, so blaming it sends the user after a permission that does not exist — an error naming the wrong cause is worse than a vague one. `ClipboardCapture` carries that distinction up from the adapter; an optional could not.

`.replaced` | `.copiedOnly(cause:reason:)`, which promises the text really is on the clipboard | `.heldForManualCopy(cause:reason:)` when we can neither write to the target nor safely borrow the clipboard, so nothing is touched and the user's unsavable clipboard survives. `cause` is a typed enum for control flow, `reason` is the sentence shown to the user, and they are separate because `reason` is copy that will get reworded and a caller in another module branching on prose breaks silently when it does. Every case is returned by a real path and pinned by a test: do not add one to look complete. **At both settings' defaults a successful rewrite is retrievable from nowhere** — replaced in the document, clipboard restored, nothing in history. That is correct, because the text is in the document and ⌘Z undoes it, but it is a change from the copy-only era and reads as a bug if you are not expecting it. **The promise the two settings compose to is about clipboard *contents*, and stops there:** `keepOutOfHistory` never reaches that path at all — only `writeDurable` reads it — and the change count necessarily moves twice, since `writeTransient` writes and the restore writes again. A manager therefore sees a write whatever the setting says; what it does with one identical to the entry it already holds is its own business, and the same third-party unknown as the markers themselves. **`observeConsumption` takes *any* selection change as proof of paste**, so `.replaced` can be returned when nothing was written — demonstrated with a selection that merely moved while still holding the user's original text. That stands, deliberately: tightening it makes a select-after-paste editor report not-consumed, which copies the rewrite it already pasted and the user duplicates a paragraph. What does **not** stand is restoring on that reading, which handed the user's clipboard back while our ⌘V was still in flight and let the target paste *their old clipboard* into their document under a `.replaced`. So the rewrite is held on the pasteboard for the whole budget. This overturns the early exit the budget comment calls a ceiling-not-a-delay, and the argument is that the two costs are not the same kind: a silent wrong write to a document that the user never asked for and cannot undo from here, against a wrong paste *they* performed inside a ~450 ms window, visible at once and fixed by copying again. `hold` blocks and must: a task would hold the borrow past the return, so a second press is refused rather than waiting, and quitting inside the window strands the rewrite on their clipboard.

Everything external is injected (`Seams.swift`). Not decoration: the central test needs "password field focused, global flag false", which cannot be staged for real, and injection is what keeps the suite off `NSPasteboard.general` and off real `CGEvent`s. `PasteboardBorrow` is injected too, defaulting to `.shared`: production needs one process-wide registry for the exclusion to mean anything, while each test suite owns its own so parallel suites cannot couple through it.

Seven seams, each with exactly one production conformance: `SystemProbe`, `AXSelectionAdapter` (read and write), `ClipboardSelectionAdapter`, `SyntheticKeystroke` (⌘C and ⌘V), and **`Tracing` → `OSLogTrace`**. A green suite proves the decisions and says nothing about whether an adapter exists, so check that list when adding a seam.

**`Tracing` is permanent, and it exists because a green suite was not enough.** Four fixes shipped to this path in one day and each was verified by a suite that agreed with the code and disagreed with the user: a fixture and a mental model can be wrong in the same direction, and then they agree. Nothing in the running app could say which branch ran, so the same wrong conclusion was reached three times from three readings of the source. `trace` is a settable property rather than an init parameter, because both initialisers are wired from the app target that `swift test` never compiles. **Never content** (root §6) — lengths, booleans, enum cases and AX roles only; a role is the app's vocabulary, not the user's. If an event needs the text to be useful, the event is wrong. The outcome is recorded in `apply`, not at each `return`, for the reason the length check sits at the end of the capture chain: a trail with a hole is worth nothing on the day it is read, and the hole is invisible until then. Tests assert the recorded *trail*, never that a logger was called.

Run: `swift build --target TextBridgeTests && xcrun xctest .build/out/Products/Debug/TextBridgeTests.xctest`. 92 tests. **Manual only, because each is pure translation over a system call with no decision in it:** `SyntheticKeystroke`, since a real `CGEvent` types into whatever the user has focused; `SystemProbe`'s three calls; the thin C wrappers in `AXSelectionAdapter`; and the live Chromium and Electron branches. Where a decision did creep in it is split out and tested: `SystemProbe.version(of:)`, `AXSelectionAdapter.isEditable` and `AXSelectionAdapter.focused(systemWide:perApp:ownedBy:)`. Rung 7 fails closed regardless, so an untested branch cannot produce a write.
